Bridge: Context Length for Masked Diffusion LMs

Practical reference for scaling MDLMs to long sequences · Prerequisites: Lesson 0003

← Core Mechanics Next → Masked Diffusion
tl;dr — Pure masked diffusion LMs (MDLM, LLaDA) share the same O(L²) attention scaling problem as transformers during each pass, but multiply it by 64× (one pass per diffusion step). For 200K-token coding tasks, this makes them VRAM-prohibitive on your L40S and slower than AR models — unless you switch to an SSM backbone (DiffuMamba), sliding window attention, or a block-autoregressive hybrid. For learning and prototyping (lessons 0004–0005), we'll use short context (256–512 tokens) where pure MDLMs shine.

Why Same Number of Passes ≠ Same VRAM

You called this out correctly. Let's be precise about what scales and how much.

Each diffusion step runs one full forward pass through the model. The cost of that pass depends on sequence length L:

Component Scaling with L What it is
Attention scores (naive) O(L²) — materialized matrix The L×L attention pattern — Flash Attention avoids materializing this
Attention FLOPs (actual compute) O(L²) — still happens Every token must attend to every other token — the math is O(L²) regardless of Flash Attn
Activations (hidden states) O(L × d_model × num_layers) All intermediate values stored for backward pass — this is the VRAM bottleneck
Embedding table lookup O(L) Negligible

Flash Attention: What It Fixes and What It Doesn't

Flash Attention tiles the attention computation so you never store the full L×L matrix in VRAM. It's essential for long sequences — but it only fixes the attention score memory, not the activation memory or the O(L²) FLOPs.

VRAM breakdown for a single forward pass (8B model, BF16, batch_size=1): L=512 L=8K L=200K Weights 16 GB 16 GB 16 GB ← constant Embedding ~4 MB ~64 MB ~1.6 GB ← negligible Activations ~0.5 GB ~2-4 GB ~50-100 GB ← ⚠️ bottleneck Attention ~0 MB (Flash Attn never stores the full matrix) ─────── Total ~16.5 GB ~20 GB ~68-118 GB ← ❌ L40S only has 48 GB

At 200K context, you can't fit even a single forward pass of an 8B transformer MDLM in 48 GB VRAM — no matter how optimized. The activations alone eat 50-100 GB. And you need 64 such passes to generate.

Important nuance: Activation checkpointing (gradient checkpointing) can reduce this during training by recomputing activations instead of storing them — but this trades memory for compute (~1.3× more FLOPs). At inference there's no backward pass, so you only store forward activations for the current step. But 50 GB of activations for a single forward pass is still over budget.

Why Training Context Length Matters for Inference

You also asked: "Must training already be prepared for longer contexts?" — and the answer is more nuanced than you might expect.

RoPE Extrapolation (The Hope)

Most MDLMs use RoPE (Rotary Position Embeddings), which supports length extrapolation — the ability to run inference at contexts longer than training. This is what lets LLaMA-3 (trained at 8K) run at 128K with techniques like NTK-aware scaling, YaRN, or dynamic NTK.

The same techniques apply to MDLMs since they also use standard attention with RoPE. So a model trained at 4K can probably extrapolate to 8K-16K with modest quality loss.

But the extrapolation gap matters:

Train → Infer Likely outcome Applies to MDLMs?
4K → 8K (2×) ✅ Minor perplexity increase, usable Yes — LLaDA can do this
4K → 32K (8×) 🟡 Significant degradation, needs NTK tuning Untested on diffusion LMs specifically
4K → 200K (50×) ❌ Garbage — too far from training distribution No — RoPE extrapolation has limits

To get 200K inference, you almost certainly need 200K training (or at least 64K-128K with aggressive extrapolation). And training at 200K with a transformer backbone means paying the O(L²) attention cost for every training step — which is why nobody has done it with pure diffusion LMs yet.

The Training Cost Wall

LLaDA 8B trained at 4K context for ~130K H800 GPU-hours. To train the same model at 200K context:

Compute multiplier ≈ (200K / 4K)² × (data scaling factor)
                   ≈ 2500 × ??? 

Reality check: 130K GPU-hours × 2500 ≈ 325M GPU-hours
                = 37,000 years on a single GPU
                = 37 years on a 1000-GPU cluster

This is why there is no 200K-context pure diffusion LM. The training cost is two to three orders of magnitude beyond what's been attempted.

The Four Levers for Long-Context MDLMs

Each lever trades one property for another. Here's how they compare:

Lever 1

🧱 Brute-Force Pretrain at Long Context

What: Train the full transformer MDLM at the target context length (e.g. 200K), relying on Flash Attention + sequence parallelism across GPUs.

VRAM cost: Very high

Efficiency: O(L²) attention FLOPs per step × O(steps) for diffusion = prohibitively expensive at scale

Verdict: ❌ Infeasible on single GPU. Needs A100/H100 cluster with hundreds of GPUs and months of training. No published diffusion LM has attempted this beyond 4K tokens.

Lever 2

🔲 Sliding Window Attention

What: Each token only attends to W neighbours instead of all L tokens. Attention becomes O(L × W) instead of O(L²).

VRAM cost: Moderate — activations still O(L × d_model), but attention is now O(W) per token

Efficiency: O(L × W) per step × O(steps) = much more affordable at long context

Caveat: Loses long-range dependencies beyond window size W. Not ideal for code where a function definition 50K tokens ago needs to be referenced.

Verdict: 🟡 Practical if your task is local (e.g., line-by-line completion). Global reasoning suffers.

Lever 3

⚡ SSM Backbone (Mamba / DiffuMamba)

What: Replace transformer attention with a State Space Model (Mamba). SSMs have O(L) complexity — constant per token regardless of total sequence length.

VRAM cost: Low — no attention matrix, no KV-cache. Activations still O(L × d_model) but no O(L²) term.

Efficiency: O(L) per step × O(steps) = best theoretical scaling for long context

Transformer at 200K:  200K² × 64 = 2.56T attention entries
Mamba at 200K:         200K × 64 = 12.8M state updates
Difference:            ≈ 200,000× fewer operations

Verdict: ✅ The architecture to watch. DiffuMamba paper claims 8.2× speedup at their tested lengths. At 200K the advantage would be much larger. Code not yet publicly released.

Lever 4

🔗 Block-Autoregressive Diffusion

What: Generate text in blocks of e.g. 256 tokens via diffusion, then chain blocks AR-style. Each block diffuses in parallel internally, but blocks depend sequentially on previous ones. (DiffusionGemma's approach.)

VRAM cost: Low per block — each block is short (256 tokens), fits easily. Cross-block context grows cumulatively.

Efficiency: O(N_blocks) serial chain + O(block_size² × steps) per block

200K output, 256-token blocks:
  - 781 blocks chained sequentially
  - Each block: 256² × 64 = 4.2M attention per block (trivial)
  - Total: 781 serial steps × attention per block
  - Serial steps: 781 — same wall-clock as AR

Verdict: 🟡 Works, but at 200K you pay 781 serial steps — same latency problem as AR, just with parallel generation inside each step. Good for very long outputs if latency isn't critical.

Bottom Line for Your Use Cases

🟢 For learning and prototyping (lessons 0004–0005)

Short context (256–512 tokens) on pure MDLM is perfect. It fits on your 8 GB local GPU, trains in minutes instead of days, and teaches you all the core mechanics. The principles transfer directly to larger contexts.

🟡 For coding at 200K tokens with an MDLM

Today: Pure masked diffusion (transformer backbone) is not the right tool. Even with Flash Attention and quantization, 64 passes at 200K won't fit in 48 GB VRAM. An AR model with KV-cache optimizations will outperform it for this specific use case.

Tomorrow (if DiffuMamba code is released): The SSM backbone changes the equation entirely. O(L) scaling × 64 diffusion steps is very feasible on your L40S at 200K. Worth watching.

🟡 Block-AR hybrid as a workaround today

If you wanted to build a long-context diffusion system right now, the block-autoregressive approach is your best bet. Each 256-token block fits easily on your L40S. The tradeoff: 781 serial steps for 200K output means ~same latency as AR.
