Part 1: 🧱 Engineering Anatomy — What Each Layer Actually Does

Your tiny MDLM has the exact same building blocks as DiffusionGemma. The only difference is scale. Let's walk through each block — not as math proofs, but as an engineer's mental model.

Goal: After this section, when you read "12-layer transformer with adaLN modulation and rotary embeddings," you should have a concrete picture of which knob turns what.

The Full Signal Path

Here's the complete forward pass of your tiny MDLM, from input to output:

Layer-by-Layer Breakdown

① Token Embedding — Turning IDs into Densities

What it is: A lookup table. Each integer token ID (0..61) maps to a row in a matrix of shape [vocab_size, d_model] = [62, 128]. The output is [B, L, 128].

What it learns: Similar tokens get similar vectors. The token ID 42 (letter 'e') ends up near token ID 3 (letter 'a') because they appear in similar contexts. The [MASK] token (ID 0) learns a vector that represents "unknown" — a kind of average of all tokens.

Why it matters: If you change vocab size (e.g., 62 → 32000 for BPE), this table grows from 62×128 = 7.9K params to 32000×128 = 4.1M params. This is often the biggest single parameter block in small models.

Fine-tuning angle: The embedding layer is worth training when you add new tokens (e.g., Portuguese characters, code symbols). It's small enough to train fully even with LoRA.

Params (your tiny model)62 × 128 = 7,936
Params (BPE, 32K vocab, 768-dim)32,000 × 768 = 24,576,000

② Position Embedding — Telling the Model Where Things Are

What it is: Another lookup table: [max_seq_len, d_model] = [128, 128]. A learned vector for each position 0..127.

What it does: Bidirectional attention has no inherent notion of order — "the cat sat" and "sat cat the" look the same without position info. The position embedding breaks this symmetry.

Why it matters: Your model uses learned absolute positions. This means it cannot generalize to sequences longer than 128 tokens — position 129 has no embedding. DiffusionGemma uses RoPE (Rotary Position Embedding) instead, which encodes position as rotations in the attention computation. RoPE can extrapolate to longer sequences.

Fine-tuning angle: If you extend context length, you either need RoPE (preferred) or interpolated position embeddings. DiffusionGemma already has this built in.

Params (your model, learned)128 × 128 = 16,384
Params (RoPE)0 — computed on the fly, no learned table

③ Time Embedding — The "What Noise Level Am I At?" Signal

What it is: A scalar t ∈ [0, 1] → sinusoidal encoding → MLP → two vectors: scale and shift, both of shape [d_model].

What it does: The sinusoidal encoding (sine/cosine at different frequencies) is the same as positional encoding in the original Transformer. It produces a high-dimensional vector that uniquely represents the noise level. The MLP transforms this into two modulation vectors.

adaLN (adaptive LayerNorm): The scale and shift vectors are applied inside each transformer block, modulating the LayerNorm. At low t (clean), the model "trusts" the input tokens — little modulation. At high t (noisy), the model relies more on learned priors — strong modulation.

Why it matters: This is the key architectural difference between your MDLM and GPT-style models. AR transformers don't need time conditioning because they always see the same "noise level" (the next token from the left). In diffusion, every timestep has a different noise level, so the model must adapt.

Fine-tuning angle: Time embeddings are tiny and can be fully trained during fine-tuning. If you change the noise schedule (e.g., cosine → uniform), you don't need to retrain the time embedding — it's just a continuous function of t.

Params (sinusoidal → MLP)(128×2)×128 + 128×2 + ... ≈ ~33K

④ Self-Attention — The "Diffusion" Engine

What it is: Each token computes queries (Q), keys (K), and values (V) from its representation. Attention = softmax(QKT / √d) · V. The output at position i is a weighted sum of all positions, where the weights depend on how relevant each position is to i.

What it learns to do in a diffusion LM:

  • Low noise (few masks): Attention learns to copy unmasked tokens to nearby masked positions — "if position 5 is 'h' and position 6 is [MASK], position 6 should probably be 'e'."
  • High noise (many masks): Attention learns global structure — "this looks like Shakespeare, so the next tokens should follow Shakespearean character patterns."
  • Bidirectional: Unlike GPT (each token only sees left context), every token sees the full sequence. This is what makes diffusion LMs able to do "in-painting" — filling blanks using both left and right context.

Multi-head: Multiple attention heads (4 in your model) let each token attend to different types of relationships simultaneously — head 1 might track subject-verb agreement, head 2 tracks character bigrams, head 3 tracks position patterns.

Cost: O(L² · d_model · n_heads) in compute and O(L² · n_heads) in memory. This is why 128-token sequences are fine but 200K is infeasible without approximations.

Fine-tuning angle: Attention weights are highly transferable. LoRA (Low-Rank Adaptation) inserts small trainable matrices into the Q and V projections, keeping the rest frozen. This is the standard approach for fine-tuning diffusion LMs.

Params per layer (your model)4 heads × (128×128) × 3 (Q,K,V) + output proj = ~200K
With LoRA (rank=8)4 heads × (128×8 + 8×128) × 2 (Q,V only) = ~16K

⑤ Feed-Forward Network — The "Thinking" Step

What it is: Two linear layers with a ReLU/GELU activation in between: FFN(x) = W2 · GELU(W1 · x + b1) + b2. The hidden dimension is typically 4× d_model (512 in your model).

What it does: Attention shares information across positions. The FFN processes each position independently — it's where the model "thinks" about what it has gathered from attention. Each position's FFN computation is identical in weights but receives different inputs.

Attribution: FFN layers are where knowledge is stored. Attention is the routing mechanism; FFN is the memory. If you want to teach the model new facts or styles, the FFN is the primary target.

Scale connection: DiffusionGemma replaces dense FFN layers with MoE (Mixture of Experts) — multiple FFN "experts" with a router that picks 2 of 16 per token. This massively increases total parameters while keeping inference cost per token nearly constant.

Params per layer (dense FFN, your model, 128→512→128)~132K
Params per layer (MoE, 8 experts, top-2, 16B total)~2B total, but only ~250M active per token

⑥ Residual Connections — Keeping the Signal Alive

What they are: output = LayerNorm(x + sublayer(x)). The input x is added back to the output of attention or FFN before the next normalization.

What they do: Without residual connections, gradients vanish in deep networks — the signal dies after ~10 layers. Residuals let gradients flow directly from the loss back to the first layer. In practice, they mean you can stack 100+ layers (DiffusionGemma has ~42 layers) without training instability.

Diffusion-specific note: Residual connections are even more important in diffusion models because the time conditioning modulates the residual stream. The scale/shift from adaLN is applied before the residual addition, letting the model decide "how much of the old signal to keep vs. how much new info to add."

Anatomy of a Single Transformer Block (Encoder)

Input h [B, L, d_model]
↓
LayerNorm + adaLN(scale, shift)
↓
Multi-Head Self-Attention (Q·K·V)
↓
← Residual: add input h
↓
LayerNorm + adaLN(scale, shift)
↓
Feed-Forward Network (GELU → Linear)
↓
← Residual: add pre-FFN input
↓
Output [B, L, d_model] (for next layer)
Your mental model after this section: A diffusion LM is a stack of blocks where (1) Attention routes information between positions, (2) FFN processes each position's gathered info, (3) adaLN tells both of them what noise level they're at, and (4) Residuals keep the whole thing trainable. Everything else is optimization.

Part 2: 🔭 DiffusionGemma — Same Building Blocks, 10,000× Larger

DiffusionGemma (Google DeepMind, 2025) takes the exact architecture you just studied — token embedding, RoPE, transformer blocks with adaLN, prediction head — and scales it to 26 billion parameters (3.8B active per token). Let's look at what changes.

What MoE Changes

In your model, every token passes through exactly the same FFN. In DiffusionGemma's MoE:

  • 16 expert FFNs replace the single FFN per layer. Each expert is a regular FFN (GELU → Linear), but with different weights.
  • A learned router looks at each token's representation and picks the top-2 most relevant experts. The token's output is the weighted average of those two experts.
  • Total parameters = 26B, but each token uses only ~3.8B of them. This means you can fit the model on fewer GPUs than a dense 26B model.
  • Fine-tuning implication: You can freeze the experts and only train the router + attention projections. Or you can add LoRA adapters to specific experts.

Block-Autoregressive: Solving Fixed-Length Output

Your tiny MDLM outputs a fixed 128 tokens. DiffusionGemma uses block-autoregressive (block-AR) to generate variable-length text:

Pure MDLM (your model)

Input:  [MASK]×128
Steps:  64 denoising steps
Output: 128 tokens (always)

You can't control length without changing the architecture.

Block-AR (DiffusionGemma)

Context: "What is 2+2?"
Step 1: diffusion → "The answer is"
Step 2: diffusion → " 4. This is because"
Output: variable length via block
        concatenation

Think of it as "diffuse a chunk, then continue."

How it works: The model generates text in blocks of 256-1024 tokens. Each block is generated via masked diffusion, conditioned on the previous blocks (which are unmasked and attend to). This gives variable total output length while keeping the diffusion quality per block.

Fine-tuning angle: If you want to fine-tune for a specific output length range (e.g., short code snippets vs. long documentation), you can fine-tune the block-AR transition mechanism.

Part 3: ⚡ DiffuMamba — When Attention Isn't the Answer

DiffuMamba replaces self-attention with a Mamba state-space model (SSM). The rest of the architecture (embedding, adaLN, FFN, head) stays. The motivation is long context — your 200K token coding use case.

What Changes vs. Your Model

Token EmbeddingSame (lookup table)
Position EncodingRemoved — Mamba handles position implicitly via its sequential recurrence
Self-AttentionReplaced by Mamba SSM block (S6 selective scan)
FFNSame (single layer per SSM block)
Time ConditioningSame (adaLN, but now modulating SSM instead of attention)
HeadSame (LN → Linear → logits)

What Mamba Gives You

Attention (your model)

O(L²)
Compute grows quadratically with sequence length

Mamba SSM

O(L)
Compute grows linearly with sequence length

Difference at 200K

~200,000×
O(L²) vs O(L) at equal hidden dim. This is the key.

But wait — why doesn't everyone use Mamba? Mamba trades quadratic compute for a hardware-unfriendly operation (the selective scan). For short sequences (≤ 2K), attention is faster due to optimized CUDA kernels. For long sequences (> 8K), Mamba wins.

How It Changes Fine-Tuning

  • No KV-cache: Mamba doesn't cache key-value pairs like attention. This means much less VRAM per token during generation — important for your L40S.
  • State size is fixed: The SSM hidden state is a small vector (16-64 elements per channel), independent of sequence length. This means VRAM during inference doesn't grow with context.
  • LoRA adapters: Same approach works — insert low-rank adapters into the SSM projection matrices (A, B, C matrices).
  • Convolution + SSM: Each Mamba layer has a convolution before the SSM. This is important for fine-tuning — it processes local patterns before the SSM handles long-range dependencies.
Updated (July 2025): Multiple DiffuMamba implementations are now available. The most production-ready is modded-diffumamba (GitHub) — a full bidirectional Mamba-3 masked diffusion LM with pre-configured model sizes from 8M to 350M params, Muon optimizer support, and FineWeb data pipeline. QLoRA Recipe 1: LLaDA 8B — Fine-tune a Pre-trained Model

Best starting point. LLaDA 8B is a pretrained masked diffusion LM available on Hugging Face. You can fine-tune it on Portuguese text or code in a few hours on your L40S.

Why LLaDA first?

  • Pre-trained weights exist (no training from scratch)
  • Same MDLM algorithm as your tiny model — you understand the architecture
  • Fits on L40S with 4-bit quantization (~5 GB VRAM for weights)
  • Active community (3.9k+ GitHub stars, responsive authors)

Recipe

StepDetails
1. Load modelLLaDA.from_pretrained("ML-GSAI/LLaDA-8B", torch_dtype=torch.bfloat16)
2. QuantizeApply 4-bit NF4 quantization (via bitsandbytes). Weights go from ~16 GB → ~5 GB.
3. Add LoRATarget: Q and V projection matrices in attention. Rank=8, Alpha=16. Adds ~8M trainable params.
4. DatasetPrepare text data as pairs (prompt, target). LLaDA expects [MASK] tokens in the target for diffusion training.
5. TrainBatch size 4-8, learning rate 2e-4, cosine schedule. Estimate: 2-4 hours for 1K steps.
6. MergeMerge LoRA weights into base model (optional). Save adapters separately for swapping.
Weights (NF4): 5 GB
Activations: 3 GB
Optimizer: 2 GB
Other: 1 GB

Total: ~11 GB VRAM — comfortably fits in 48 GB. Room for larger batch size.

Recommendation: Start here. LLaDA + QLoRA on your L40S is the quickest path to a fine-tuned diffusion LM you can actually use.

LoRA Recipe 2: DiffusionGemma 26B — LoRA Fine-Tuning (Active=3.8B)

For when you need Google's quality. DiffusionGemma is 26B total but only 3.8B active per token. This means it can technically fit on a single L40S for inference. Fine-tuning is trickier.

The MoE Fine-Tuning Challenge

MoE models have all 26B parameters in VRAM even if only 3.8B are active. The inactive experts stay in memory — they just aren't computed. So you need VRAM for the full 26B, not the active 3.8B.

Options

ApproachVRAMTraining TimeQuality
QLoRA on single L40S (4-bit)~18 GB (weights) + ~10 GB (acts+optim) = 28 GB ✅~8-12 hoursGood (4-bit quantization)
LoRA on single L40S (BF16)~52 GB (weights) ❌ — doesn't fit——
LoRA on 2× L40S (BF16, FSDP)~26 GB per GPU ✅~4-6 hoursBest (no quantization)
Full fine-tune (any)Needs 8× A100 ❌DaysBest

Recommendation for Single L40S

# Pseudocode for QLoRA on DiffusionGemma
model = DiffusionGemma.from_pretrained("google/diffusiongemma-26b")
model = quantize_4bit(model, dtype=torch.bfloat16)  # 28 GB
peft_config = LoRAConfig(
    r=8, lora_alpha=16,
    target_modules=["q_proj", "v_proj"],  # note: no expert modules
    # Only attention projections. Freeze all expert FFNs.
)
model = get_peft_model(model, peft_config)
train(model, dataset, batch_size=2, ...)
# ~8 hours for 500 fine-tuning steps

Key insight: You're only training attention projections (Q, V) — about ~25M trainable params out of 26B. The MoE experts stay frozen because they're too large and already well-trained on general text. This is fine for style/task adaptation but won't teach new knowledge.

Precautions: (1) Set up gradient checkpointing to save activations. (2) Use Flash Attention 2. (3) Monitor expert load balancing — LoRA on attention can shift expert selection. (4) Test with a small dataset first.

Distillation Recipe 3: Distill LLaDA 8B → Your Tiny Architecture

For when you want to own the entire model. Distill knowledge from a large diffusion LM (teacher) into your own smaller architecture (student). You control every parameter.

Why distill?

  • Your student model can be architecture-optimized for your use case (e.g., shorter context, Portuguese vocab)
  • You own the weights — no license restrictions
  • Model is small enough to deploy on edge or share with others
  • The student can run inference at 10-100× lower cost than the teacher

Recipe

StepDetails
1. Design studentYour tiny MDLM architecture, scaled up: ~20M params, 8 layers, 256-dim, BPE tokenizer (8K vocab), 512 context.
2. Generate teacher outputsRun LLaDA 8B on your domain data. Save the forward pass at intermediate noise levels — not just final tokens, but the distribution (logits) at each diffusion step.
3. Train studentStandard diffusion training + distillation loss: KL divergence between teacher and student logits at the same noise level. The student learns to "imitate" the teacher's internal denoising process.
4. ValidateCompare student outputs to teacher. Fine-tune distillation schedule if needed (e.g., weigh high-noise steps more).
Distillation vs. LoRA: LoRA fine-tunes on top of a large model. Distillation creates a new small model. LoRA is faster and better quality. Distillation gives you full ownership and deployment flexibility. For early experiments, start with LoRA. For production at scale, consider distillation.

2× L40S Recipe 4: Multi-Node with FSDP (2× L40S)

For when you need BF16 precision. With two L40S nodes and FSDP (Fully Sharded Data Parallelism), you can fine-tune DiffusionGemma at full BF16 precision — no quantization loss.

Architecture

ComponentSetup
GPU 0Holds layers 0-21 (bottom half) + optimizer states for its shard
GPU 1Holds layers 22-42 (top half) + optimizer states for its shard
CommunicationAllGather for activations during forward pass. ReduceScatter for gradients during backward pass.
InterconnectNVLink (600 GB/s) strongly preferred. InfiniBand (100-200 GB/s) works. Ethernet (1-10 GB/s) will bottleneck.

Recipe

# Using Hugging Face + PyTorch FSDP
# On each node:
torchrun --nproc_per_node=1 \
  --nnodes=2 \
  --node_rank=$RANK \
  --master_addr=$MASTER_ADDR \
  fine_tune.py \
  --model google/diffusiongemma-26b \
  --sharding_strategy FULL_SHARD \
  --batch_size 4 \
  --gradient_accumulation_steps 8 \
  --lora_r 8 \
  --lora_target_modules q_proj,v_proj \
  --output_dir ./diffusiongemma-lora

# Each GPU sees ~13 GB of weights + ~6 GB activations + ~4 GB optimizer
# Total per GPU: ~23 GB ✅

Key considerations:

  • FSDP communication overhead: expect 10-20% slower than single-GPU training (but 2× batch size)
  • Both GPUs must have the same CUDA compute capability (L40S = Ada Lovelace, should match)
  • Network latency between nodes matters — if they're in the same datacenter rack, latency is ~100μs. If across regions, FSDP will be too slow and you should use DeepSpeed ZeRO-3 instead.
  • Your potential cluster (nodes with 2× L40S each) would give 4 GPUs total — enough for full BF16 LoRA on DiffusionGemma with batch size 16.

🧰 Complementary Resource: modded-diffumamba

Since this lesson was written, modded-diffumamba by ChrisLundquist has emerged as a ready-to-run implementation that bridges your tiny MDLM and the production-scale architectures above. It's a modded-nanogpt-style research repo using Karpathy's autoresearch methodology.

What it is

A self-contained implementation of a masked diffusion LM with bidirectional Mamba-3 backbone, auto-detecting the best available SSM backend (Mamba3 Triton → Mamba2 → pure PyTorch fallback). Single-file training, pre-configured model sizes, and automated experiment runners.

Architecture (directly comparable to your tiny MDLM)

Input tokens → Embed → [BiMamba3Block × N] → RMSNorm → LM Head → Logits

Each BiMamba3Block:
  1. AdaLN (conditioned on noise sigma)
  2. Forward Mamba-3 scan
  3. Backward Mamba-3 scan (input flipped)
  4. h_fwd + h_bwd (additive merge — NOT attention!)
  5. Residual + AdaLN + SwiGLU MLP + residual

Compare to your tiny MDLM's Embed → [Attention + FFN × 4] → Head: the attention block is replaced by forward+backward SSM scans. Everything else — embeddings, AdaLN conditioning, residual connections, prediction head — stays the same.

Adapting to Portuguese Data

The repo uses GPT-2 tokenizer (50K BPE) on FineWeb-10B. To adapt:

  1. Tokenizer: Replace with a BPE tokenizer trained on Portuguese text. data/tokenize.py handles streaming tokenization from raw parquet files.
  2. Data: Point --data_dir at your Portuguese corpus. The .bin shard format is just uint16 token IDs with a simple header — trivial to generate.
  3. Model: Change vocab_size in the config to match your new tokenizer's vocabulary. The embedding layer will be the main size change.
  4. SSM backend: Auto-detected. On your L40S (NVIDIA), it'll use Mamba3 Triton kernels (~105K tok/s inference).

What This Means for Your Build Decision

The repo demonstrates that Mamba-based MDLMs are not just viable but superior to transformer MDLMs at small scale: lower repetition, no KV-cache, linear O(L) scaling, and a validated training recipe with Muon optimizer. The 111M param model achieves gen-PPL 54.3 — competitive with the MDLM paper's 82 at 169M. For your L40S, the base (231M) and large (350M) configs are well within budget and would serve as excellent starting points for Portuguese+coding experiments.

Recommendation: If you're building from scratch rather than fine-tuning, start with --config base (231M) on your Portuguese data. It's the sweet spot: large enough for meaningful language understanding, small enough to iterate quickly (hours, not days), and the SSM backbone avoids the repetition problems that plague transformer MDLMs at this scale.
