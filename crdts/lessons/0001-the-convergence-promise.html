Lesson 1 · CRDTs

The Convergence Promise

Two whiteboards get the same edits in a different order — and must end up identical. Build the smallest data type that guarantees it.

By the end of this lesson you will:
  • Be able to state exactly what "conflict-free" buys you — the convergence promise.
  • Have built an LWW-Register in ~6 lines of JS and watched two replicas converge no matter the order.
  • Know the three laws a merge must obey, and the one update LWW silently throws away.

1 · The whiteboard problem

Your harness is building a collaborative whiteboard: shapes on a shared canvas, syncing peer-to-peer, working offline. Picture one rectangle. Alice and Bob both have it on screen. The train goes into a tunnel — both are now offline.

  • Alice recolors the rectangle red.
  • Bob, independently, recolors it blue.

They reconnect. Each must send the other what they did. The brutal fact of peer-to-peer is that you cannot control how those messages arrive: they can be reordered, delayed, duplicated, or batched. The naive fix — "last message to arrive wins" — means Alice's board and Bob's board pick the winner based on network timing. Different timing, different result: the two boards diverge and stay diverged. That is the bug CRDTs exist to kill.

A CRDT (Conflict-free Replicated Data Type) is a data structure whose merge depends only on the data, never on the order it arrived in. Get that, and every replica that has seen the same edits agrees — automatically, with no central server and no locking.[crdt.tech]

2 · The promise, stated precisely

This is the guarantee, called Strong Eventual Consistency:

Any two replicas that have received the same set of updates hold the same state — regardless of the order, duplication, or delay of delivery.[Shapiro 2011]

Note what it does not promise: it won't read your mind about which color "should" win. It promises only that everyone ends up agreeing on the same answer. Picking a sensible answer is the data type's job — which is why there's a whole zoo of CRDTs, one per kind of data. Today we build the simplest.

3 · Build it: the LWW-Register

A register is a cell holding one value — perfect for one property of one shape: its color, or its x. LWW = Last-Writer-Wins. The trick: don't store just the value, store the value tagged with when it was written. Paste this into a Node REPL or your browser console:

// An LWW-Register: a value, plus when and who wrote it.
const reg = (value, ts, replica) => ({ value, ts, replica });

// merge: keep the write with the higher timestamp.
// On a tie, the replica id decides — so the rule is fully deterministic.
function merge(a, b) {
  if (a.ts !== b.ts)   return a.ts > b.ts ? a : b;
  return a.replica > b.replica ? a : b;
}

That's the entire CRDT. Now reproduce the tunnel. Alice wrote red at logical time 3; Bob wrote blue at time 5:

const alice = reg('red',  3, 'A');
const bob   = reg('blue', 5, 'B');

merge(alice, bob).value              // 'blue'  — ts 5 beats ts 3
merge(bob, alice).value              // 'blue'  — swap the order: same answer
merge(merge(alice, bob), bob).value  // 'blue'  — Bob's msg arrives twice: no change
merge(merge(bob, alice), alice).value// 'blue'  — any tangle of re-delivery: still blue

Run all four lines. Every one returns blue. That is the convergence promise, in your own console: reorder the messages, duplicate them, nest the merges however the network felt like — the rectangle ends up blue on both boards. No server adjudicated. The math did.

Where does ts come from? Wall-clock time is tempting but treacherous (clocks disagree). Real systems use a logical clock — a counter that only ever goes up — often a Lamport timestamp, with the replica id as the tiebreak you saw above. We'll build that properly in a later lesson; for now, "a number that only increases" is enough.

4 · Why it converges — the three laws

The four lines above weren't luck. merge works because it obeys three properties — the only theory you need today:

LawMeansDefeats
Commutativemerge(a,b) = merge(b,a)reordering
Associativemerge(merge(a,b),c) = merge(a,merge(b,c))batching / grouping
Idempotentmerge(a,a) = aduplicate delivery

Reordering, batching, and duplication are exactly the three things a p2p network does to your messages. A merge that is immune to all three cannot be pushed off the single answer the data determines. That immunity is what "conflict-free" literally means — and in Lesson 2 we'll see these three laws are the definition of a semilattice, the structure underneath every CRDT.

5 · The honest catch

Look again at what happened: Alice's red didn't merge with Bob's blue — it was silently discarded. LWW converges by throwing one writer's work away. For a shape's color that's usually fine (somebody had to win). For "Bob deleted the shape while Alice was still dragging it," or "two people typing in the same sticky note," dropping a whole update is a data-loss bug. Different data needs a merge that keeps more — that's the whole rest of the course (sets of shapes, then sequences for text and z-order).
