The Provenance Detective

Before you can remove anything cleanly, you have to know who installed it. Here's how to find out — every time, in under a minute.

The win: by the end, you can take any command on your PATH and prove which of four sources put it there — apt, snap, a make install, or a manual symlink. That single fact decides the correct way to uninstall it. Get this wrong and you delete a binary while leaving its libraries, configs, and data behind — exactly the cruft you're trying to clear.

Why provenance is the whole game

Every "uninstall" question reduces to one prior question: who manages this file? Each source keeps its own ledger, and only its own tool can settle the account cleanly:

  • apt records every file it placed in a database (dpkg). Ask the database.
  • snap mounts each app as a read-only image under /snap. There's nothing to "delete" — you unmount it via snap remove.
  • make install copies raw files into /usr/local and tells nobody. No ledger exists; you must reconstruct one.
  • manual symlink is just a pointer you (or a tool like Stow) created. Removing it is removing the link.

The map: a few FHS landmarks

The Filesystem Hierarchy Standard isn't trivia here — it's the map that makes provenance readable from the path alone. The crucial boundary:

PathOwnerWhat it tells you
/usr/bin, /usr/libthe distroAlmost certainly apt. dpkg should claim it.
/usr/local/…youThe package manager will never put anything here. So if it's here, it's a manual install or symlink.
/snap/…snapdA snap. Read-only squashfs mount.
/opt/…3rd-partySelf-contained vendor blob; treat like a manual install.
The /usr vs /usr/local split is the single most useful fact in this whole topic. /usr belongs to the distribution; /usr/local belongs to you. The same binary name can exist in both — and which one wins on your PATH is a classic source of "why am I running the old version?" confusion.

The procedure (memorise this shape)

command -v git                      # 1. where is it?  →  /usr/bin/git
readlink -f "$(command -v git)"     # 2. resolve symlinks to the REAL file
ls -l "$(command -v git)"           # 3. was the PATH entry itself a link?
dpkg -S "$(readlink -f "$(command -v git)")"   # 4. does apt claim it?

Read the results top-down and the source falls out:

  1. Resolved path under /snap? → snap. Done.
  2. Else dpkg -S names a package? → apt. Done.
  3. Else it's unowned. Was the PATH entry a symlink (step 3)? → manual symlink.
  4. Else it's a real file in /usr/local or /opt? → make install.

/usr/bin/python3
$ ls -l /usr/bin/python3

The subtlety in E

/usr/bin/python3 is a symlink — but that does not make it a "manual symlink." The distinction is who created the link: dpkg itself ships symlinks inside packages. That's exactly why step 4 resolves the link with readlink -f before asking dpkg -S. A symlink only means "manual" when it lives in /usr/local and dpkg disclaims the resolved target. Order of operations is everything: resolve, then ask the database, then judge the link.

Do this on your own machine

Pick three commands you actually use and run the procedure on each:

for c in git curl your-favourite-tool; do
  echo "== $c =="
  p="$(command -v "$c")"; ls -l "$p"; dpkg -S "$(readlink -f "$p")" 2>&1 | head -1
done

Try to find at least one tool that dpkg disclaims — something living in /usr/local. That's a future cleanup target, and the subject of an upcoming lesson on uninstalling a make install that has no make uninstall.
