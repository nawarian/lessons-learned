Tuya Local Control — Cheat Sheet

The compressed essentials for driving a Tuya/Izy bulb over the LAN. Keep this open while you work.

The three secrets

Local control of any Tuya device needs exactly these three values. Lose any one and you cannot talk to the device locally.

SecretWhat it isWhere it comes fromCan it change?
Device ID (gwId)Permanent per-device identifiertinytuya scan or the cloud wizardOnly if you re-pair / factory reset
IP addressThe bulb's address on your LANtinytuya scan (UDP discovery)Yes — DHCP can move it. Pin with a reservation.
Local keyAES key encrypting the LAN trafficCloud wizard, or offline extractionYes — rotates when you re-pair the device in the app

Glossary

TermMeaning
DP / datapointA numbered control channel on the device. For a bulb: power, mode, brightness, colour, colour-temp each have a DP index (e.g. "20", "21"…).
DPSThe dict of all datapoint values — what status() returns.
Protocol versionThe LAN wire format: 3.1, 3.3, 3.4, or 3.5. Must match the bulb's firmware or you get empty/garbled replies.
Local key16-byte AES key. Encrypts all LAN payloads. Per-device, rotates on re-pair.
gwId / devIdThe device ID.
Port 6668The TCP port the Tuya LAN protocol speaks on.

Setup once

python3 -m venv ~/.venvs/tuya && . ~/.venvs/tuya/bin/activate
pip install tinytuya

Core commands

# 1. Find devices on the LAN (IP + device ID, key shown if known)
python -m tinytuya scan

# 2. One-time: fetch local keys from Tuya cloud into devices.json
python -m tinytuya wizard

# 3. Re-scan and merge keys with live IPs / DP snapshots
python -m tinytuya scan        # reads devices.json automatically

Control a bulb (Python)

import tinytuya
d = tinytuya.BulbDevice('DEVICE_ID', 'IP', 'LOCAL_KEY', version=3.3)
d.set_version(3.3)              # try 3.4 / 3.5 if status() is empty

d.status()                     # -> {'dps': {...}}  the DPS dict
d.turn_on(); d.turn_off()
d.set_brightness(500)          # range ~10–1000
d.set_colourtemp(500)          # warm..cool, ~0–1000
d.set_colour(255, 80, 0)       # R,G,B  (switches to colour mode)
d.set_white(800, 500)          # brightness, colourtemp
Version probing. If status() returns {} or an error, the protocol version is wrong. Walk it: 3.3 → 3.4 → 3.5 → 3.1. Newer Tuya firmware (3.4/3.5) adds a session handshake; tinytuya handles it once the version matches.

Failure → first thing to check

SymptomMost likely cause
scan finds nothingController not on the same 2.4 GHz subnet / VLAN as the bulb; UDP broadcast blocked.
Found, but status() emptyWrong protocol version, or wrong/missing local key.
Worked, now refusesLocal key rotated (you re-paired in the app) — re-run the wizard. Or IP changed.
Connection refused on 6668The app holds a connection — Tuya bulbs accept essentially one local session. Close the app.

Local key, offline (no cloud API)

The key is a random 16-char value assigned at pairing — read it, don't compute it. The Intelbras/Izy app caches it on your phone:

# modern (MMKV):  /data/data/<package>/files/thingmmkv/preferences_global_key
# older  (XML):   /data/data/<package>/shared_prefs/preferences_global_key<n>.xml
adb shell pm list packages | grep -iE 'intelbras|izy|tuya|smart'   # find <package>

Copy that one file to your PC, then extract cleartext pairs (records are plain JSON, MMKV isn't encrypted):

import re, sys
blob = open(sys.argv[1],'rb').read().decode('latin-1','ignore')
for m in re.finditer(r'"localKey":"(\w{16})"', blob):
    w = blob[max(0,m.start()-2000):m.start()+2000]
    d = re.search(r'"devId":"(\w{18,25})"', w)
    print(d.group(1) if d else '?', m.group(1))

Cross-check each devId against your scan output, then hand-write devices.json (id, key, ip, version).

The honest boundary

"No vendor API" means no cloud at control time. The easy key-fetch (wizard) reads the key from Tuya's cloud once. After that, every command above is pure LAN. Fully-offline key extraction (packet capture / app file) avoids even that one touch — harder, covered separately.
